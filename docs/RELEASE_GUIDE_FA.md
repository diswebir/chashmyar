# راهنمای صاحب پروژه: ساخت مخزن و انتشار خودکار

[شروع سریع GitHub](GITHUB_QUICKSTART_FA.md) · [صفحهٔ اصلی](../README.md) · [English: CI and release](CI_AND_RELEASE.md)

این پروژه برای **انتشار خودکار پس از push به شاخهٔ `main`** تنظیم شده است: گردش Actions نسخهٔ پایهٔ جدید و منتشرنشده یا Patch بعدی را انتخاب می‌کند، برنامه را برای ویندوز x64 می‌سازد و در صورت موفقیت بررسی‌های خودش Release را منتشر می‌کند. ساخت تگ و زدن دکمهٔ Publish در حالت عادی لازم نیست. **این گردش با این سورس هنوز در مخزن واقعی شما اجرا نشده است**؛ نخستین اجرای GitHub و عملکرد واقعی برنامه روی ویندوز باید بررسی شوند.

> **مهم:** انتشار پس از آزمون‌های خودکار، منتظر تأیید یا آزمون دستی نمی‌ماند. اگر باید پیش از عمومی‌شدن، انسان برنامه را روی ویندوز بررسی کند، پیش از push/merge به `main` این کار را انجام دهید یا سیاست گردش را تغییر دهید. ساخت روی runner ویندوز به معنی آزمون عملی تمام قابلیت‌های نصب‌شده نیست.

## ۱. یک‌بار: آماده‌سازی مخزن و کلید

۱. سورس کامل را استخراج و مخزن موجود [`diswebir/chashmyar`](https://github.com/diswebir/chashmyar) را clone کنید؛ تاریخچه، تگ‌ها و فایل‌های نسخه‌های قبلی را حفظ کنید. پوشهٔ `.github`، lockfileها، `assets/branding`، آیکن‌ها، کل `src-tauri/vendor/tao` و تست‌ها را منتقل کنید. `node_modules`، `dist`، `target`، `release`، دادهٔ شخصی و کلیدها را commit نکنید.
۲. پیش از push، طبق **[راهنمای امن کلید و Secrets](UPDATER_SIGNING_FA.md)**، `TAURI_SIGNING_PRIVATE_KEY` و در صورت نیاز `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` را به repository secrets و `CHASHMYAR_UPDATER_PUBLIC_KEY` را به repository variables اضافه کنید. نسخه‌های قدیمی باید ابتدا به اولین انتشار امضاشده به‌صورت دستی ارتقا یابند. کلید خصوصی را در سورس نگذارید و آن و رمز را امن پشتیبان بگیرید.
۳. اجرای Actions و actionهای پین‌شده را مجاز کنید. سیاست مخزن و ruleset تگ‌ها باید به `github-actions[bot]` اجازهٔ انتشار بدهد؛ job انتشار `contents: write` می‌خواهد. برای دستورهای کپی، commit و push بدون force به [شروع سریع](GITHUB_QUICKSTART_FA.md) مراجعه کنید. updater در سورس به آدرس همین مخزن محدود شده است.

## ۲. اولین انتشار و انتشارهای بعدی

شمارهٔ پایهٔ سورس این بسته `2.4.9` است. اگر هنگام تخصیص بیشترین تگ پایدار `v2.4.8` باشد، انتشار موفق **`v2.4.9`** می‌شود و push موفق بعدی معمولاً `v2.4.10` خواهد بود. اگر تگ برابر یا بالاتر وجود داشته باشد، Patch بعد از بزرگ‌ترین تگ پایدار انتخاب می‌شود و تگ قبلی بازنویسی نمی‌شود. انتشار ناموفق، لغوشده یا ردشده الزاماً نسخه‌ای تولید نمی‌کند. برای جایگزینی پرتابل معیوب قبلی [راهنمای اصلاح](../FIX_2.4.8_FA.md) را ببینید.

پس از push:

1. به **Actions → Automatic Windows release** بروید و اجرای مربوط به commit خود را باز کنید. jobهای تخصیص نسخه، ساخت/آزمون ویندوز و انتشار باید موفق شوند. مرحلهٔ `Audit embedded production UI in both staged Windows executables` برنامهٔ استخراج‌شده از نصب‌کننده و پرتابل را جداگانه و بدون پنجره برای حالت تولید، کلید و هش رابط با `dist` مقایسه می‌کند. گردش جداگانهٔ **CI** نیز اجرا می‌شود، ولی انتشار منتظر نتیجهٔ آن workflow جداگانه نیست؛ خودِ گردش انتشار آزمون‌های دیگرش را انجام می‌دهد. این بررسی‌ها جای اجرای تعاملی WebView2 و آزمون قابلیت‌های بومی را نمی‌گیرند.
2. بعد از موفقیت، **Releases** را باز کنید. Release باید منتشر شده و دارای نشان **Latest** باشد؛ در مخزن Public عموم به آن دسترسی دارند. نشانی `https://github.com/diswebir/chashmyar/releases/latest/download/latest.json` باید فایل همین انتشار را بدهد، چون برنامه از همین مسیر استفاده می‌کند. اگر گردش شکست بخورد، ممکن است فقط یک Draft موقت غیرعمومی یا یک تگ باقی بماند؛ بدون بررسی آن را Publish نکنید.
3. وجود هشت دارایی را بررسی کنید: دو EXE، دو فایل `.exe.sig`، `latest.json`، `SHA256SUMS.txt`، `LICENSE` و `THIRD_PARTY_NOTICES.txt`. GitHub آرشیوهای Source code را جداگانه نشان می‌دهد.
4. هش‌ها را از همان Release بررسی کنید و برنامه را طبق چک‌لیست ویندوز در بخش ۴ آزمایش کنید. برای مثال، شماره را با نسخهٔ واقعی جایگزین کنید:

```powershell
Get-FileHash .\ChashmYar_2.4.9_x64-setup.exe -Algorithm SHA256
Get-FileHash .\ChashmYar-2.4.9-portable.exe -Algorithm SHA256
```

هش‌ها ممکن است در هر ساخت تغییر کنند. `SHA256SUMS.txt` به‌تنهایی هویت ناشر را تأیید نمی‌کند. امضای updater با گواهی ناشر Authenticode متفاوت است؛ بدون گواهی جداگانه ممکن است SmartScreen هشدار دهد. WebView2 نیز لازم است.

برای تغییرات بعدی، در مسیر پروژه:

```powershell
git checkout main
git pull --ff-only origin main
# تغییرات موردنظر را انجام دهید، تست و بازبینی کنید
git add .
git status --short
git commit -m "Describe the change"
git push origin main
```

هر push تازه به `main` یک اجرای انتشار درخواست می‌کند؛ push به شاخهٔ دیگر یا push دستی تگ آن را شروع نمی‌کند. `git tag` یا افزایش دستی Patch برای گردش عادی لازم نیست. فایل‌های ذخیره‌شدهٔ کاربران و تنظیمات برنامه با این تغییرات گردش انتشار دست‌کاری نمی‌شوند.

## ۳. روش شماره‌گذاری، ایمنی و محدودیت‌ها

- نسخهٔ پایه در `main` **خودکار تغییر یا commit نمی‌شود**؛ بنابراین pull کردن شاخهٔ اصلی با commit انتشار تداخل نمی‌کند. در job انتشار، از همان commit ارسالی یک commit فرزند ساخته و فقط روی تگ قرار می‌گیرد. پنج فایل نسخه در سورس تگ، آرشیو Source code، نصب‌کننده و پرتابل با شمارهٔ جدید هماهنگ‌اند. از نسخهٔ نوشته‌شده در `package.json` شاخهٔ `main` نتیجه نگیرید که آخرین Release همان است؛ صفحهٔ Releases یا تگ را ببینید.
- برای تغییر عمدی نسخهٔ پایه، می‌توان `node scripts/version.mjs set 2.5.0` را اجرا و همهٔ فایل‌های تغییرکرده را با هم commit کرد. اگر تمام تگ‌های پایدار پایین‌تر از آن باشند، اولین انتشار `v2.5.0` است؛ در غیر این صورت یک Patch پس از بزرگ‌ترین تگ انتخاب می‌شود. فقط نسخه‌های عددی پایدار پشتیبانی می‌شوند و هر جزء حداکثر `65535` است؛ اگر Patch بزرگ‌ترین تگ به این سقف برسد، ابتدا پایهٔ اصلی/فرعی بالاتری انتخاب کنید. `CHANGELOG.md` خودکار نوشته نمی‌شود.
- گردش ابتدا در محیط خواندنی تست و build انجام می‌دهد. فقط job مستقل انتشار مجوز `contents: write` دارد. پس از تطبیق محتوای کامل فایل‌های نسخه با سورس، یک Draft موقت می‌سازد؛ هشت فایل را بدون جایگزینی آپلود می‌کند، امضا، نسخه، اندازه و SHA-256 گزارش‌شدهٔ GitHub را تطبیق می‌دهد و تگ‌ها را دوباره می‌خواند. سپس Draft را **خودکار** منتشر و Latest تعیین و با چند تلاش محدود از GitHub تأیید می‌کند؛ تگ یا دارایی موجود را overwrite نمی‌کند. اگر تأیید Latest شکست بخورد، ممکن است Release پیش‌تر عمومی شده باشد؛ وضعیت واقعی را بررسی کنید. انتشارهای دستی هم‌زمان همچنان می‌توانند با این بررسی رقابت کنند؛ دسترسی و انتشار دستی را محدود و هماهنگ کنید.
- اجرای هم‌زمان انتشارها صف‌بندی شده است. GitHub حداکثر **۱۰۰ اجرای منتظر** را در این صف نگه می‌دارد و اضافه بر آن ممکن است لغو شود. ترتیب شروع هم برای همهٔ رویدادها تضمین نشده است: اگر اجرای commit قدیمی پس از انتشار commit جدیدتر برسد، برای جلوگیری از بازگشت نسخه رد می‌شود. force-push، تگ‌های ناسازگار، برخورد تگ و خطاهای شبکه یا آزمون هم می‌توانند مانع انتشار شوند. بنابراین «هر push» تضمین بی‌قیدوشرط نیست؛ وضعیت Actions را بررسی کنید.
- اجرای مجدد commitی که قبلاً منتشر شده، سلامت Release موجود را بررسی می‌کند و آن را بازنویسی یا برای همان commit نسخهٔ جدید ایجاد نمی‌کند. در صورت نیاز به نسخهٔ تازه، commit و push تازه انجام دهید. گردش `workflow_dispatch` روی `main` برای بازیابی نیز موجود است.
- اگر job انتشار شکست خورد، تا قبل از انتشار نسخهٔ جدیدتر، ابتدا در همان اجرای ناموفق **Re-run failed jobs** را امتحان کنید. این روش می‌تواند از artifact همان build استفاده کند؛ artifact گردش ۱۴ روز نگه داشته می‌شود. بازسازی کامل ممکن است فایل اجرایی با هش متفاوت بسازد؛ در این صورت، برای جلوگیری از جایگزینی فایل‌های Draft، انتشار عمداً متوقف می‌شود. علت را در Actions و وضعیت تگ/Draft بررسی کنید؛ نسخهٔ عمومی را حذف یا فایل‌های آن را بی‌صدا عوض نکنید.

برای تغییر وابستگی‌ها، پیش از commit `npm run licenses:generate` را اجرا کنید، خروجی و تعهدات مجوزها را بازبینی و `THIRD_PARTY_NOTICES.txt` را همراه lockfileها ثبت کنید. job انتشار، اعلان ثبت‌شده را کنترل می‌کند.

## ۴. چک‌لیست آزمون ویندوز

این چک‌لیست **خودکار نیست** و جلوی انتشار را نمی‌گیرد. در صورت امکان پیش از push، و در هر حال برای تأیید نسخه، روی ویندوز واقعی یا ماشین مجازی امن انجام شود:

- [ ] هر هشت دارایی، از جمله دو امضا و `latest.json`، وجود دارند و هش فایل‌های دانلودشده با `SHA256SUMS.txt` همان نسخه یکسان است.
- [ ] نصب‌کننده در ویندوز x64 نصب، اجرا و حذف می‌شود؛ پرتابل نیز جداگانه اجرا می‌شود. در نبود WebView2، حالت دریافت/نصب آن بررسی می‌شود.
- [ ] نشان چشم انتخاب‌شده در آیکن فایل، پنجره و سینی سیستم و در هدر برنامه دیده می‌شود؛ سینی و نوار وظیفهٔ روشن/تاریک و مقیاس‌های DPI مختلف بررسی شده‌اند. بررسی PNG/ICO یا مرورگر، نمایش واقعی اکسپلورر و سینی ویندوز را ثابت نمی‌کند.
- [ ] پس از بستن و اجرای دوباره، زبان، تم، تنظیمات و گزارش مورد انتظار باقی می‌مانند؛ داده‌های قبلی قبل از آزمون پشتیبان‌گیری شده‌اند.
- [ ] اعلان پیش از استراحت، دکمهٔ × و تعویق؛ تمرین کوتاه؛ ابزارک؛ تم روشن و تاریک؛ و امتیازهای بدون داده و دارای داده بررسی شده‌اند. ویجت چسبیده پس از دو ثانیه هاور باز شود، خروج زودهنگام شمارش را لغو کند و تنظیم دلخواه جدید پس از راه‌اندازی مجدد حفظ شود.
- [ ] محافظ چشم با روشنایی نرم‌افزاری فعال باشد؛ اعلان خودکار چشم‌یار، تمرین کوتاه و اعلان به‌روزرسانی را چند بار نمایش دهید و روی «افزودن زمان» کلیک کنید. فیلتر پیش از نمایش و در تمام مدت کلیک باید برقرار بماند، دکمه‌ها کلیک‌پذیر باشند و نمایش خودکار فوکوس را ندزدد. با دوربین گوشی و روی چند مانیتور، DPI و HDR مختلف بررسی کنید. این تغییر هنوز در محیط ویندوز تعاملی تأیید نشده است.
- [ ] با دو انتشار متوالی امضاشده توسط یک کلید، ابتدا نسخهٔ قبلیِ دارای updater را برای هر دو نوع اجرا کنید: دانلود باید خودکار باشد اما پیش از تأیید هیچ نصب/راه‌اندازی مجددی انجام نشود؛ رد تأیید، پذیرش، حفظ داده‌ها و توقف تایمر آزموده شوند. در پرتابل، مسیر دارای فاصله/فارسی و نبود دسترسی نوشتن، باقی‌ماندن نسخهٔ قبلی یا فایل پشتیبان در خطا و راه‌اندازی مجدد بررسی شود. قطع اینترنت و خطای امضا را در محیط آزمایشی مجزا و بدون تغییر دارایی انتشار عمومی تست کنید.
- [ ] در Notepad و یک مرورگر، داخل یک کادر متن کلیک و پیوسته تایپ کنید؛ در زمان نمایش **خودکار** هشدار ۳۰ ثانیه‌ای و تمرین کوتاه، نشانگر و متن نباید از کادر خارج شوند. هر دو حالت نمایش/پنهان‌سازیِ تکراری را بیازمایید. سپس عمداً روی × و دکمه‌های تعویق کلیک کنید و عملکردشان و دسترسی با صفحه‌کلید را بررسی کنید؛ تعامل عمدی می‌تواند فوکوس را تغییر دهد. هشدار را با صدای روشن/خاموش نیز امتحان کنید. پیش‌نمایش بازشده از تنظیمات جای آزمایش تایمر خودکار در یک برنامهٔ دیگر را نمی‌گیرد.
- [ ] روشن/خاموش‌کردن و جابه‌جایی سریع دمای رنگ، زمان‌بندی، حالت رنگ‌ایمن و بستن برنامه در حین تغییر رنگ بررسی شده‌اند؛ پس از خروج نباید تغییر رنگِ تازه‌ای از worker باقی بماند. محدودیت HDR و درایور را جداگانه ثبت کنید.
- [ ] در محیط امن ویندوز x64، ابتدا خاموش‌بودن پیش‌فرض و حفظ تنظیمات قدیمی را بررسی کنید. برای هر سه پروفایل دید رنگی، شدت صفر، چند شدت میانی و ۱۰۰، تعویض سریع، خاموش‌کردن، بستن/بازکردن و ذخیره‌ماندن انتخاب را روی محتوای متنوع و با کاربر نهایی مقایسه کنید. بهترشدن همهٔ رنگ‌ها فرض نشود.
- [ ] جداگانه بررسی کنید کلید محافظ چشم، دما/گاما، روشنایی، زمان‌بندی و پروفایل‌های قبلی مستقل‌اند؛ فیلتر دید رنگی با ورود به برنامهٔ رنگ‌ایمن متوقف و با خروج برمی‌گردد (تأخیر تشخیص را اندازه بگیرید). چند نمایشگر، HDR، بازی، ضبط و اسکرین‌شات را حسب نیاز مقایسه کنید.
- [ ] با Magnifier و یک ابزار افکت تمام‌صفحهٔ دیگر، تداخل قبل و بعد از فعال‌سازی، عدم بازنویسی افکت مشاهده‌شده، «تلاش دوباره»، خروج امن، قطع اجباری و بازیابی را آزمون کنید. خواندن/نوشتن اتمیک نیست و همهٔ تداخل‌ها قابل تشخیص نیستند؛ بازگردانی crash تضمین نمی‌شود. این بخش هنوز روی ویندوز واقعی تأیید نشده است.
- [ ] قفل سخت‌گیرانه و نگه‌داشتن Ctrl+Shift برای خروج اضطراری، با فعال بودن این گزینه و در محیط امن، بررسی شده‌اند. هم‌زمان کلیک سریع، سینی سیستم و بازگشت رنگ/گاما نیز آزموده شوند.
- [ ] در نصب تازه، اجرای خودکار ویندوز و شروع تایمر، زمان‌بندی شب و فاصلهٔ ۲۰ ثانیهٔ تمرین بررسی شده‌اند؛ در ارتقا، تنظیمات ذخیره‌شدهٔ قبلی بدون بازنویسی حفظ شده‌اند.
- [ ] در نصب تازه اعلان و تمرین کوتاه و شروع/پایان استراحت و جریمه بی‌صدا هستند؛ با روشن‌کردن «سیستم ← پخش صدای هشدار» صدای آن‌ها شنیده می‌شود و انتخاب پس از بستن/اجرای مجدد باقی می‌ماند. ارتقا با صدای قبلاً روشن و خاموش نیز جداگانه بررسی شده است.
- [ ] با خاموش بودن رنگ‌ایمن و با دما/روشنایی مختلف، منوی راست‌کلیک، اعلان‌ها و هر نمایشگر آزمایش شده‌اند. Win+Shift+S و یک ضبط کوتاه در نرم‌افزار دلخواه را با تصویر بدون فیلتر مقایسه کنید؛ HDR، چند مانیتور و روش‌های ضبط ممکن است متفاوت باشند. حذف لایه از ضبط در ویندوز ۱۰ ۲۰۰۴+ فقط برای روش‌های سازگار درخواست می‌شود.
- [ ] روی نمایشگر واقعی، راست‌کلیک دسکتاپ و File Explorer، زیرمنوها و پنجره‌های برنامه‌های مختلف چند بار باز و با نسخهٔ قبلی مقایسه شده‌اند؛ کلیک از لایه عبور می‌کند و خاموش‌کردن محافظ/رنگ‌ایمن، جابه‌جایی سریع تنظیمات و خروج عادی باعث گیرکردن نمی‌شود. برای مشاهدهٔ فلش از چشم یا ویدئوی گوشی استفاده کنید، نه ضبط سازگاری که عمداً لایه را حذف می‌کند. به علت تحویل ناهم‌زمان رویداد ممکن است همچنان یک فریم دیده شود.
- [ ] تفاوت امضای updater با گواهی Authenticode، هشدار احتمالی SmartScreen و نیاز WebView2 در توضیحات مشخص‌اند. `LICENSE` و اعلان وابستگی‌ها و تعهدات مجوزها بررسی شده‌اند.

برای عیب‌یابی، در پوشهٔ پرتابل و با شمارهٔ واقعی:

```powershell
.\ChashmYar-2.4.9-portable.exe --self-test
```

نتیجه در پنجره و `%LOCALAPPDATA%\ChashmYar\startup.log` ثبت می‌شود. لاگ ممکن است مسیر کاربر را داشته باشد؛ پیش از اشتراک‌گذاری آن را پاک‌سازی کنید.

## ۵. ساخت محلی

روی ویندوز با پیش‌نیازهای [راهنمای توسعه](DEVELOPMENT.md) و پس از تنظیم متغیرهای کلید مطابق [راهنمای امضا](UPDATER_SIGNING_FA.md):

```powershell
powershell -ExecutionPolicy Bypass -File .\build-windows.ps1
```

نصب‌کننده و پرتابل در `release/windows/` و مجموعهٔ همراه هش و اعلان‌ها در `release/staging/` قرار می‌گیرند. ساخت محلی به‌تنهایی به GitHub چیزی آپلود نمی‌کند. اگر آگاهانه انتشار دستی لازم است، اول گردش خودکار همان تگ را متوقف و وضعیت تگ و Draft موجود را بررسی کنید؛ ایجاد Release هم‌زمان برای یک تگ باعث برخورد و توقف ایمن می‌شود.

## ۶. خطاهای متداول

- **Release دیده نمی‌شود یا job نهایی خطا دارد:** اجرای **Automatic Windows release** و هر سه job آن را بررسی کنید. Release یک مخزن Private عمومی نیست. Draft نشانهٔ انتشار ناتمام است. اگر خطا بعد از فرمان انتشار رخ داده باشد، ممکن است Release از قبل عمومی شده اما کنترل نهایی شکست خورده باشد؛ وضعیت و هش‌های همان Release را پیش از هر اقدامی بررسی کنید.
- **خطای مجوز یا 403:** Actions و `contents: write`، محدودیت سازمان، ruleset تگ‌ها و اجازهٔ `github-actions[bot]` را بررسی کنید. توکن شخصی را داخل سورس قرار ندهید.
- **کلید یا امضا نامعتبر است:** نام Secret و Variable، رمز و مطابقت کلید عمومی/خصوصی را طبق [راهنمای کلید](UPDATER_SIGNING_FA.md) بررسی کنید؛ مقادیر محرمانه را چاپ یا ارسال نکنید. کلید جدید برای کاربرانی که کلید قدیمی دارند نیازمند مسیر ارتقای دستی است.
- **Mismatch، تگ تکراری یا Draft ناسازگار:** متن خطای Actions را بخوانید. ابتدا همان job شکست‌خورده را با artifact اصلی دوباره اجرا کنید. تگ یا دارایی منتشرشده را جابه‌جا یا overwrite نکنید. اگر فایل ناقص یا Draft دیگری وجود دارد، پیش از هر تغییر دستی علت و مالکیت آن را بررسی کنید.
- **انتشار قدیمی skip شد یا در صف لغو شد:** گردش از انتشار commit قدیمی بعد از نسخهٔ جدیدتر جلوگیری می‌کند و صف ۱۰۰ مورد محدودیت دارد. جزئیات اجرا را ببینید؛ در صورت نیاز تغییرات را در commit تازه به `main` برسانید.
- **خطای دانلود NSIS یا WebView2/HTTP 504:** سرویس یا شبکه ممکن است موقتاً در دسترس نباشد؛ پس از بررسی، اجرای ناموفق را دوباره آغاز کنید. دریافت WebView2 هنگام نصب نیز ممکن است شبکه بخواهد.
- **خطای lockfile یا وابستگی:** `npm ci` و `cargo metadata --locked --manifest-path src-tauri/Cargo.toml` را بررسی کنید؛ تغییرات عمدی وابستگی و lockfileها را با هم commit و اعلان مجوزها را به‌روز کنید.
- **ساخت موفق ولی عملکرد اشتباه:** آزمون مرورگری اجرای قلاب، گاما، ضبط یا نصب‌کننده نیست. در محیط ویندوز واقعی بازتولید کنید و لاگ پاک‌سازی‌شده را بررسی کنید. کنترل متقاطع و آزمون مرورگر در این محیط جای اجرای واقعی صدا، فوکوس، کلیک WebView2، به‌روزرسانی پرتابل، گاما و ضبط روی ویندوز را نمی‌گیرند.
