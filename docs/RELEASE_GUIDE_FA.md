# راهنمای صاحب پروژه: ساخت مخزن و انتشار خودکار

[شروع سریع GitHub](GITHUB_QUICKSTART_FA.md) · [صفحهٔ اصلی](../README.md) · [English: CI and release](CI_AND_RELEASE.md)

این پروژه برای **انتشار خودکار پس از push به شاخهٔ `main`** تنظیم شده است: گردش Actions شمارهٔ Patch را یک واحد بالا می‌برد، برنامه را برای ویندوز x64 می‌سازد و در صورت موفقیت بررسی‌های خودش Release را منتشر می‌کند. ساخت تگ و زدن دکمهٔ Publish در حالت عادی لازم نیست. **این گردش هنوز در مخزن واقعی شما اجرا نشده است**؛ نخستین اجرای GitHub و عملکرد واقعی برنامه روی ویندوز باید بررسی شوند.

> **مهم:** انتشار پس از آزمون‌های خودکار، منتظر تأیید یا آزمون دستی نمی‌ماند. اگر باید پیش از عمومی‌شدن، انسان برنامه را روی ویندوز بررسی کند، پیش از push/merge به `main` این کار را انجام دهید یا سیاست گردش را تغییر دهید. ساخت روی runner ویندوز به معنی آزمون عملی تمام قابلیت‌های نصب‌شده نیست.

## ۱. یک‌بار: آماده‌سازی مخزن

1. بستهٔ سورس جدید را کامل استخراج کنید. پوشهٔ مخفی `.github` باید کنار `README.md` و `package.json` باشد؛ lockfileها، `assets/branding`، `src-tauri/icons`، همهٔ `src-tauri/vendor/tao` و تست‌ها را نیز حفظ کنید. پوشه‌های `node_modules`، `dist`، `src-tauri/target` و `release` به مخزن اضافه نمی‌شوند؛ هنگام ساخت دوباره ایجاد می‌شوند. بستهٔ سورس فایل اجرایی جدید ندارد و فایل‌های اجرایی قدیمی ۲.۴.۳ نشان جدید را ندارند. برای ارسال سورس نیازی به ساخت محلی نیست.
2. در [GitHub](https://github.com/new) یک مخزن خالی بسازید و اگر دانلود برای همه لازم است، آن را **Public** انتخاب کنید. در مخزن Private، حتی Release منتشرشده فقط برای افراد دارای دسترسی قابل مشاهده است. برای مخزن خالی، گزینه‌های ایجاد README و مجوز را در سایت غیرفعال بگذارید؛ آن‌ها در بسته وجود دارند.
3. در تنظیمات مخزن، **Actions → General** را باز کنید و مطمئن شوید اجرای GitHub Actions و actionهای استفاده‌شده مجاز است. job انتشار در workflow مجوز `contents: write` درخواست می‌کند؛ سیاست سازمان یا مخزن نباید نوشتن تگ و Release را مسدود کند. در صورت وجود ruleset برای تگ‌ها، دسترسی لازم به `github-actions[bot]` را با احتیاط بررسی کنید. توکن شخصی داخل سورس لازم نیست.
4. [Git for Windows](https://git-scm.com/downloads/win) را نصب کنید. به‌جای خط فرمان می‌توانید از [GitHub Desktop](https://desktop.github.com/) استفاده کنید؛ پوشهٔ کامل از جمله `.github` باید ثبت شود.
5. PowerShell را **در ریشهٔ پروژه**، جایی که `package.json` دیده می‌شود، باز کنید. نام و ایمیل commit خود را در صورت نیاز تنظیم کنید:

```powershell
git config --global user.name "نام شما"
git config --global user.email "ایمیل شما"
git init -b main
git add .
git status --short
```

در `git status` باید سورس، `LICENSE`، مستندات، lockfileها و `.github/workflows` دیده شوند؛ نباید فایل تنظیمات شخصی، گواهی امضا، `node_modules`، `dist`، `target` یا `release` دیده شوند. پس از بازبینی:

```powershell
git commit -m "Prepare ChashmYar for GitHub"
# OWNER و REPOSITORY را با حساب و مخزن خود جایگزین کنید:
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

Git Credential Manager یا GitHub Desktop می‌تواند ورود را انجام دهد؛ رمز یا توکن را داخل آدرس، سورس یا workflow نگذارید. برای push فایل‌های workflow با توکن شخصی ممکن است مجوز workflow لازم باشد. اگر مخزن از قبل تاریخچه دارد، به‌جای `git init` یا push اجباری، آن را clone و تغییرات را با تاریخچهٔ موجود ادغام کنید.

## ۲. اولین انتشار و انتشارهای بعدی

شمارهٔ پایهٔ سورس این بسته `2.4.3` است. اگر مخزن تازه باشد و تگ پایدار بالاتری وجود نداشته باشد، اولین push موفق به `main` معمولاً **`v2.4.4`** را منتشر می‌کند؛ push موفق بعدی معمولاً `v2.4.5` می‌شود. اگر از قبل تگ‌های پایدار بالاتری وجود داشته باشد، شماره از بزرگ‌ترین نسخهٔ پایدارِ موجود یا نسخهٔ پایه، هرکدام بزرگ‌تر باشد، یک Patch جلو می‌رود. انتشار ناموفق، لغوشده یا ردشده الزاماً نسخه‌ای تولید نمی‌کند.

پس از push:

1. به **Actions → Automatic Windows release** بروید و اجرای مربوط به commit خود را باز کنید. jobهای تخصیص نسخه، ساخت/آزمون ویندوز و انتشار باید موفق شوند. گردش جداگانهٔ **CI** نیز اجرا می‌شود، ولی انتشار منتظر نتیجهٔ آن workflow جداگانه نیست؛ خودِ گردش انتشار بررسی دارایی‌های نشان، لینک‌های محلی مستندات، آزمون‌های منطق، شبیه‌سازی انتشار و مرورگر/mock را انجام می‌دهد. این آزمون‌ها ظاهر یا عملکرد بومی ویندوز را تأیید نمی‌کنند.
2. بعد از موفقیت، **Releases** را باز کنید. Release باید منتشر شده باشد؛ در مخزن Public عموم به آن دسترسی دارند. اگر گردش شکست بخورد، ممکن است فقط یک Draft موقت غیرعمومی یا یک تگ باقی بماند؛ بدون بررسی آن را Publish نکنید.
3. وجود پنج دارایی را بررسی کنید: `ChashmYar_<VERSION>_x64-setup.exe`، `ChashmYar-<VERSION>-portable.exe`، `SHA256SUMS.txt`، `LICENSE` و `THIRD_PARTY_NOTICES.txt`. GitHub آرشیوهای Source code را جداگانه نشان می‌دهد.
4. هش‌ها را از همان Release بررسی کنید و برنامه را طبق چک‌لیست ویندوز در بخش ۴ آزمایش کنید. برای مثال، شماره را با نسخهٔ واقعی جایگزین کنید:

```powershell
Get-FileHash .\ChashmYar_2.4.4_x64-setup.exe -Algorithm SHA256
Get-FileHash .\ChashmYar-2.4.4-portable.exe -Algorithm SHA256
```

هش‌ها ممکن است در هر ساخت تغییر کنند. `SHA256SUMS.txt` سلامت فایل‌های همان Release را بررسی می‌کند، **امضای ناشر نیست**؛ فایل‌های پیش‌فرض امضای دیجیتال ندارند و ممکن است SmartScreen هشدار دهد. WebView2 نیز لازم است.

برای تغییرات بعدی، در مسیر پروژه:

```powershell
git checkout main
git pull --ff-only origin main
# تغییرات موردنظر را انجام دهید، تست و بازبینی کنید
git add .
git status --short
git commit -m "Describe the change"
git push origin main
```

هر push تازه به `main` یک اجرای انتشار درخواست می‌کند؛ push به شاخهٔ دیگر یا push دستی تگ آن را شروع نمی‌کند. `git tag` یا افزایش دستی Patch برای گردش عادی لازم نیست. فایل‌های ذخیره‌شدهٔ کاربران و تنظیمات برنامه با این تغییرات گردش انتشار دست‌کاری نمی‌شوند.

## ۳. روش شماره‌گذاری، ایمنی و محدودیت‌ها

- نسخهٔ پایه در `main` **خودکار تغییر یا commit نمی‌شود**؛ بنابراین pull کردن شاخهٔ اصلی با commit انتشار تداخل نمی‌کند. در job انتشار، از همان commit ارسالی یک commit فرزند ساخته و فقط روی تگ قرار می‌گیرد. پنج فایل نسخه در سورس تگ، آرشیو Source code، نصب‌کننده و پرتابل با شمارهٔ جدید هماهنگ‌اند. از نسخهٔ نوشته‌شده در `package.json` شاخهٔ `main` نتیجه نگیرید که آخرین Release همان است؛ صفحهٔ Releases یا تگ را ببینید.
- برای تغییر عمدی نسخهٔ پایهٔ اصلی/فرعی، می‌توان `node scripts/version.mjs set 2.5.0` را اجرا و همهٔ فایل‌های تغییرکرده را با هم commit کرد. در این مثال، اولین انتشار پس از آن دست‌کم `v2.5.1` خواهد بود، نه `v2.5.0`. فقط نسخه‌های عددی پایدار پشتیبانی می‌شوند؛ هر جزء حداکثر `65535` است. `CHANGELOG.md` خودکار نوشته نمی‌شود.
- گردش ابتدا در محیط خواندنی تست و build انجام می‌دهد. فقط job مستقل انتشار مجوز `contents: write` دارد. پس از تطبیق سورس، نسخه و تگ، یک Draft موقت می‌سازد؛ پنج فایل را بدون جایگزینی آپلود می‌کند، اندازه و SHA-256 گزارش‌شدهٔ GitHub را تطبیق می‌دهد و **خودکار** Draft را منتشر می‌کند. تگ یا داراییِ منتشرشده هرگز خودکار overwrite نمی‌شود.
- اجرای هم‌زمان انتشارها صف‌بندی شده است. GitHub حداکثر **۱۰۰ اجرای منتظر** را در این صف نگه می‌دارد و اضافه بر آن ممکن است لغو شود. ترتیب شروع هم برای همهٔ رویدادها تضمین نشده است: اگر اجرای commit قدیمی پس از انتشار commit جدیدتر برسد، برای جلوگیری از بازگشت نسخه رد می‌شود. force-push، تگ‌های ناسازگار، برخورد تگ و خطاهای شبکه یا آزمون هم می‌توانند مانع انتشار شوند. بنابراین «هر push» تضمین بی‌قیدوشرط نیست؛ وضعیت Actions را بررسی کنید.
- اجرای مجدد commitی که قبلاً منتشر شده، سلامت Release موجود را بررسی می‌کند و آن را بازنویسی یا برای همان commit نسخهٔ جدید ایجاد نمی‌کند. در صورت نیاز به نسخهٔ تازه، commit و push تازه انجام دهید. گردش `workflow_dispatch` روی `main` برای بازیابی نیز موجود است.
- اگر job انتشار شکست خورد، تا قبل از انتشار نسخهٔ جدیدتر، ابتدا در همان اجرای ناموفق **Re-run failed jobs** را امتحان کنید. این روش می‌تواند از artifact همان build استفاده کند؛ artifact گردش ۱۴ روز نگه داشته می‌شود. بازسازی کامل ممکن است فایل اجرایی با هش متفاوت بسازد؛ در این صورت، برای جلوگیری از جایگزینی فایل‌های Draft، انتشار عمداً متوقف می‌شود. علت را در Actions و وضعیت تگ/Draft بررسی کنید؛ نسخهٔ عمومی را حذف یا فایل‌های آن را بی‌صدا عوض نکنید.

برای تغییر وابستگی‌ها، پیش از commit `npm run licenses:generate` را اجرا کنید، خروجی و تعهدات مجوزها را بازبینی و `THIRD_PARTY_NOTICES.txt` را همراه lockfileها ثبت کنید. job انتشار، اعلان ثبت‌شده را کنترل می‌کند.

## ۴. چک‌لیست آزمون ویندوز

این چک‌لیست **خودکار نیست** و جلوی انتشار را نمی‌گیرد. در صورت امکان پیش از push، و در هر حال برای تأیید نسخه، روی ویندوز واقعی یا ماشین مجازی امن انجام شود:

- [ ] هر پنج دارایی وجود دارند و هش فایل‌های دانلودشده با `SHA256SUMS.txt` همان نسخه یکسان است.
- [ ] نصب‌کننده در ویندوز x64 نصب، اجرا و حذف می‌شود؛ پرتابل نیز جداگانه اجرا می‌شود. در نبود WebView2، حالت دریافت/نصب آن بررسی می‌شود.
- [ ] نشان چشم انتخاب‌شده در آیکن فایل، پنجره و سینی سیستم و در هدر برنامه دیده می‌شود؛ سینی و نوار وظیفهٔ روشن/تاریک و مقیاس‌های DPI مختلف بررسی شده‌اند. بررسی PNG/ICO یا مرورگر، نمایش واقعی اکسپلورر و سینی ویندوز را ثابت نمی‌کند.
- [ ] پس از بستن و اجرای دوباره، زبان، تم، تنظیمات و گزارش مورد انتظار باقی می‌مانند؛ داده‌های قبلی قبل از آزمون پشتیبان‌گیری شده‌اند.
- [ ] اعلان پیش از استراحت، دکمهٔ × و تعویق؛ تمرین کوتاه؛ ابزارک؛ تم روشن و تاریک؛ و امتیازهای بدون داده و دارای داده بررسی شده‌اند.
- [ ] در Notepad و یک مرورگر، داخل یک کادر متن کلیک و پیوسته تایپ کنید؛ در زمان نمایش **خودکار** هشدار ۳۰ ثانیه‌ای و تمرین کوتاه، نشانگر و متن نباید از کادر خارج شوند. هر دو حالت نمایش/پنهان‌سازیِ تکراری را بیازمایید. سپس عمداً روی × و دکمه‌های تعویق کلیک کنید و عملکردشان و دسترسی با صفحه‌کلید را بررسی کنید؛ تعامل عمدی می‌تواند فوکوس را تغییر دهد. هشدار را با صدای روشن/خاموش نیز امتحان کنید. پیش‌نمایش بازشده از تنظیمات جای آزمایش تایمر خودکار در یک برنامهٔ دیگر را نمی‌گیرد.
- [ ] روشن/خاموش‌کردن و جابه‌جایی سریع دمای رنگ، زمان‌بندی، حالت رنگ‌ایمن و بستن برنامه در حین تغییر رنگ بررسی شده‌اند؛ پس از خروج نباید تغییر رنگِ تازه‌ای از worker باقی بماند. محدودیت HDR و درایور را جداگانه ثبت کنید.
- [ ] قفل سخت‌گیرانه و نگه‌داشتن Ctrl+Shift برای خروج اضطراری، با فعال بودن این گزینه و در محیط امن، بررسی شده‌اند. هم‌زمان کلیک سریع، سینی سیستم و بازگشت رنگ/گاما نیز آزموده شوند.
- [ ] در نصب تازه، اجرای خودکار ویندوز و شروع تایمر، زمان‌بندی شب و فاصلهٔ ۲۰ ثانیهٔ تمرین بررسی شده‌اند؛ در ارتقا، تنظیمات ذخیره‌شدهٔ قبلی بدون بازنویسی حفظ شده‌اند.
- [ ] در نصب تازه اعلان و تمرین کوتاه و شروع/پایان استراحت و جریمه بی‌صدا هستند؛ با روشن‌کردن «سیستم ← پخش صدای هشدار» صدای آن‌ها شنیده می‌شود و انتخاب پس از بستن/اجرای مجدد باقی می‌ماند. ارتقا با صدای قبلاً روشن و خاموش نیز جداگانه بررسی شده است.
- [ ] با خاموش بودن رنگ‌ایمن و با دما/روشنایی مختلف، منوی راست‌کلیک، اعلان‌ها و هر نمایشگر آزمایش شده‌اند. Win+Shift+S و یک ضبط کوتاه در نرم‌افزار دلخواه را با تصویر بدون فیلتر مقایسه کنید؛ HDR، چند مانیتور و روش‌های ضبط ممکن است متفاوت باشند. حذف لایه از ضبط در ویندوز ۱۰ ۲۰۰۴+ فقط برای روش‌های سازگار درخواست می‌شود.
- [ ] روی نمایشگر واقعی، راست‌کلیک دسکتاپ و File Explorer، زیرمنوها و پنجره‌های برنامه‌های مختلف چند بار باز و با نسخهٔ قبلی مقایسه شده‌اند؛ کلیک از لایه عبور می‌کند و خاموش‌کردن محافظ/رنگ‌ایمن، جابه‌جایی سریع تنظیمات و خروج عادی باعث گیرکردن نمی‌شود. برای مشاهدهٔ فلش از چشم یا ویدئوی گوشی استفاده کنید، نه ضبط سازگاری که عمداً لایه را حذف می‌کند. به علت تحویل ناهم‌زمان رویداد ممکن است همچنان یک فریم دیده شود.
- [ ] بی‌امضا بودن فایل‌ها، SmartScreen و WebView2 در توضیحات مشخص‌اند. `LICENSE` و اعلان وابستگی‌ها و تعهدات مجوزها بررسی شده‌اند.

برای عیب‌یابی، در پوشهٔ پرتابل و با شمارهٔ واقعی:

```powershell
.\ChashmYar-2.4.4-portable.exe --self-test
```

نتیجه در پنجره و `%LOCALAPPDATA%\ChashmYar\startup.log` ثبت می‌شود. لاگ ممکن است مسیر کاربر را داشته باشد؛ پیش از اشتراک‌گذاری آن را پاک‌سازی کنید.

## ۵. ساخت محلی

روی ویندوز با پیش‌نیازهای [راهنمای توسعه](DEVELOPMENT.md):

```powershell
powershell -ExecutionPolicy Bypass -File .\build-windows.ps1
```

نصب‌کننده و پرتابل در `release/windows/` و مجموعهٔ همراه هش و اعلان‌ها در `release/staging/` قرار می‌گیرند. ساخت محلی به‌تنهایی به GitHub چیزی آپلود نمی‌کند. اگر آگاهانه انتشار دستی لازم است، اول گردش خودکار همان تگ را متوقف و وضعیت تگ و Draft موجود را بررسی کنید؛ ایجاد Release هم‌زمان برای یک تگ باعث برخورد و توقف ایمن می‌شود.

## ۶. خطاهای متداول

- **Release دیده نمی‌شود یا job نهایی خطا دارد:** اجرای **Automatic Windows release** و هر سه job آن را بررسی کنید. Release یک مخزن Private عمومی نیست. Draft نشانهٔ انتشار ناتمام است. اگر خطا بعد از فرمان انتشار رخ داده باشد، ممکن است Release از قبل عمومی شده اما کنترل نهایی شکست خورده باشد؛ وضعیت و هش‌های همان Release را پیش از هر اقدامی بررسی کنید.
- **خطای مجوز یا 403:** Actions و `contents: write`، محدودیت سازمان، ruleset تگ‌ها و اجازهٔ `github-actions[bot]` را بررسی کنید. توکن شخصی را داخل سورس قرار ندهید.
- **Mismatch، تگ تکراری یا Draft ناسازگار:** متن خطای Actions را بخوانید. ابتدا همان job شکست‌خورده را با artifact اصلی دوباره اجرا کنید. تگ یا دارایی منتشرشده را جابه‌جا یا overwrite نکنید. اگر فایل ناقص یا Draft دیگری وجود دارد، پیش از هر تغییر دستی علت و مالکیت آن را بررسی کنید.
- **انتشار قدیمی skip شد یا در صف لغو شد:** گردش از انتشار commit قدیمی بعد از نسخهٔ جدیدتر جلوگیری می‌کند و صف ۱۰۰ مورد محدودیت دارد. جزئیات اجرا را ببینید؛ در صورت نیاز تغییرات را در commit تازه به `main` برسانید.
- **خطای دانلود NSIS یا WebView2/HTTP 504:** سرویس یا شبکه ممکن است موقتاً در دسترس نباشد؛ پس از بررسی، اجرای ناموفق را دوباره آغاز کنید. دریافت WebView2 هنگام نصب نیز ممکن است شبکه بخواهد.
- **خطای lockfile یا وابستگی:** `npm ci` و `cargo metadata --locked --manifest-path src-tauri/Cargo.toml` را بررسی کنید؛ تغییرات عمدی وابستگی و lockfileها را با هم commit و اعلان مجوزها را به‌روز کنید.
- **ساخت موفق ولی عملکرد اشتباه:** آزمون مرورگری اجرای قلاب، گاما، ضبط یا نصب‌کننده نیست. در محیط ویندوز واقعی بازتولید کنید و لاگ پاک‌سازی‌شده را بررسی کنید. نسخهٔ ۲.۴.۳ در این محیط به‌صورت متقاطع ساخته شده و صدا، فوکوس، کلیک WebView2، مسیر رویداد ویندوز، گاما و ضبط واقعاً روی ویندوز اجرا نشده‌اند.
