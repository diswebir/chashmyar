# راهنمای صاحب پروژه: ساخت مخزن و انتشار نسخه‌ها

این راهنما فرض می‌کند شما صاحب مخزن GitHub هستید. پروژه عمداً طوری تنظیم شده که **تگ نسخه فایل‌ها را می‌سازد، اما انتشار نهایی را خودتان تأیید می‌کنید**. هیچ حساب، مخزن، توکن یا انتشار واقعی از طرف این راهنما ساخته نشده است.

## ۱. یک‌بار: آماده‌سازی و ساخت مخزن

1. بستهٔ سورس آماده را کامل از ZIP استخراج کنید. پوشهٔ مخفی `.github` باید در کنار `README.md` و `package.json` باشد. پوشه‌های `node_modules`، `dist`، `src-tauri/target` و `release` نباید به مخزن اضافه شوند؛ هنگام ساخت دوباره ایجاد می‌شوند.
2. در [GitHub](https://github.com/new) یک مخزن جدید بسازید؛ برای دانلود عمومی، آن را **Public** انتخاب کنید. اگر قرار است سورس فعلی اولین محتوای آن باشد، گزینه‌های ایجاد README، مجوز و `.gitignore` در سایت را غیرفعال بگذارید؛ این فایل‌ها داخل بسته هستند.
3. [Git for Windows](https://git-scm.com/downloads/win) را نصب کنید. می‌توانید به‌جای خط فرمان از [GitHub Desktop](https://desktop.github.com/) استفاده کنید، اما باید پوشهٔ کامل پروژه، از جمله `.github`، ثبت شود.
4. PowerShell را **در پوشهٔ ریشهٔ پروژه** باز کنید؛ جایی که `package.json` دیده می‌شود. اگر Git برای اولین بار استفاده می‌شود، نام و ایمیل commit را با اطلاعات خودتان تنظیم کنید. ایمیل خصوصی GitHub از نوع `users.noreply.github.com` نیز قابل استفاده است.

```powershell
git config --global user.name "نام شما"
git config --global user.email "ایمیل شما"

git init -b main
git add .
git status --short
```

در خروجی `git status` باید فایل‌های سورس، `LICENSE`، `docs`، lockfileها و `.github/workflows` دیده شوند. نباید `node_modules`، `dist`، `target`، `release`، فایل تنظیمات شخصی یا گواهی امضا دیده شوند. فهرست را پیش از ادامه بررسی کنید.

```powershell
git commit -m "Prepare ChashmYar for GitHub"
# OWNER و REPOSITORY را با نام حساب و مخزن خود جایگزین کنید:
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

Git Credential Manager یا GitHub Desktop می‌تواند ورود را انجام دهد؛ رمز یا توکن را داخل آدرس، سورس یا فایل workflow نگذارید. اگر از توکن استفاده می‌کنید، برای push فایل‌های workflow باید مجوز مربوط به workflow نیز داشته باشد. اگر مخزن از قبل تاریخچه دارد، از `git init`/push اجباری روی آن استفاده نکنید؛ ابتدا آن را clone و تغییرات را با تاریخچهٔ موجود ادغام کنید.

5. در صفحهٔ مخزن، برگهٔ **Actions** را باز کنید و اگر لازم بود Actions را فعال کنید. اجرای **CI** روی `main` آزمون‌ها را اجرا می‌کند. سبز شدن آن به معنی آزمون واقعی برنامهٔ ویندوز نیست.
6. در **Settings → Security / Code security**، قابلیت گزارش خصوصی آسیب‌پذیری را در صورت دسترس‌بودن فعال کنید. تنظیمات سازمان ممکن است اجرای Actions یا مجوز نوشتن Release را محدود کند.

## ۲. انتشار اولین نسخهٔ موجود: ۲.۳.۱

در سورس این بسته شمارهٔ نسخه `2.3.1` است. بعد از push شدن شاخهٔ `main` و سبز شدن CI، در همان پوشه:

```powershell
npm ci
npm run version:check
git status
# فقط اگر تغییرات موردنظر ثبت و push شده‌اند:
git tag -a v2.3.1 -m "ChashmYar v2.3.1"
git push origin v2.3.1
```

تگ باید روی همان commit موردنظر باشد. تگ فقط با قالب پایدار `vMAJOR.MINOR.PATCH` و شمارهٔ برابر با فایل‌های پروژه پذیرفته می‌شود؛ `v2.3.1-beta` در گردش فعلی پشتیبانی نمی‌شود.

اکنون در GitHub:

1. به **Actions → Build Windows release draft** بروید و اجرای مربوط به تگ را باز کنید. ساخت ممکن است چند دقیقه طول بکشد. اگر شکست خورد، گزارش همان مرحله را بخوانید و بخش عیب‌یابی این راهنما را ببینید.
2. بعد از موفقیت، در صفحهٔ اصلی مخزن وارد **Releases** شوید. یک مورد **Draft** با عنوان نسخه ظاهر می‌شود؛ پیش‌نویس فقط برای افراد مجاز قابل مشاهده است و هنوز عمومی نیست.
3. در Assets وجود این پنج فایل را بررسی کنید: نصب‌کنندهٔ `...-setup.exe`، نسخهٔ `...-portable.exe`، `SHA256SUMS.txt`، `LICENSE` و `THIRD_PARTY_NOTICES.txt`. GitHub معمولاً آرشیوهای Source code را جداگانه نیز نمایش می‌دهد.
4. فایل‌ها را دانلود، هش‌ها را بررسی و نصب‌کننده و پرتابل را **روی ویندوز واقعی یا ماشین مجازی ویندوز** طبق چک‌لیست بخش ۴ آزمایش کنید. ساخت در runner ویندوز و آزمون مرورگری به‌تنهایی اجرای واقعی قابلیت‌های سیستم را تأیید نمی‌کند.
5. یادداشت‌های خودکار را بازبینی و تغییرات و محدودیت‌ها را اصلاح کنید. در صفحهٔ ویرایش پیش‌نویس، پس از رضایت، **Publish release** را بزنید. تازه پس از این کار، کاربران مخزن عمومی می‌توانند فایل‌ها را در Releases دانلود کنند.

برای هر فایل، مقدار SHA-256 خروجی فرمان زیر را با خط هم‌نام در `SHA256SUMS.txt` مقایسه کنید:

```powershell
Get-FileHash .\ChashmYar_2.3.1_x64-setup.exe -Algorithm SHA256
Get-FileHash .\ChashmYar-2.3.1-portable.exe -Algorithm SHA256
```

هش‌های هر ساخت ممکن است با ساخت قبلی متفاوت باشند؛ از `SHA256SUMS.txt` همان Release استفاده کنید، نه یک مقدار قدیمی. هش سلامت انتقال را بررسی می‌کند، **امضای ناشر نیست**.

## ۳. انتشار نسخه‌های بعدی

مثال: نسخهٔ بعدی `2.3.2`. عددها را با نسخهٔ واقعی خودتان جایگزین کنید.

```powershell
git checkout main
git pull --ff-only origin main
npm ci
node scripts/version.mjs set 2.3.2
npm run version:check
```

اسکریپت شماره را در `package.json`، هر دو محل لازم در `package-lock.json`، `src-tauri/tauri.conf.json`، `src-tauri/Cargo.toml` و ورودی خود پروژه در `src-tauri/Cargo.lock` هماهنگ می‌کند. نسخه‌های آزمایشی/پسونددار و اجزای بزرگ‌تر از ۶۵۵۳۵ برای این جریان رد می‌شوند. `CHANGELOG.md` را نیز برای نسخهٔ جدید دستی به‌روز کنید. اگر وابستگی‌ها را عوض کرده‌اید، اعلان‌ها را بازتولید و بررسی کنید:

```powershell
npm run licenses:generate
npm run test:logic
npm run test:compat
npm run test:release
npm run build
npx playwright install chromium
npm run test:ui:all
```

سپس تغییرات را بررسی، ثبت و ارسال کنید:

```powershell
git status
git diff --check
git add .
git diff --cached
git commit -m "Release 2.3.2"
git push origin main
```

بعد از سبز شدن CI، تگ را ایجاد و ارسال کنید:

```powershell
git tag -a v2.3.2 -m "ChashmYar v2.3.2"
git push origin v2.3.2
```

گردش Actions فایل‌ها را ساخته و پیش‌نویس می‌سازد. دوباره مراحل بررسی ویندوز و Publish در بخش ۲ را انجام دهید. **برای هر انتشار عمومی از یک تگ جدید استفاده کنید**؛ تگ نسخهٔ منتشرشده را جابه‌جا یا فایل‌های آن را بی‌صدا جایگزین نکنید. اجرای مجدد گردش برای پیش‌نویس می‌تواند دارایی‌های آن را جایگزین کند اما یادداشت‌های پیش‌نویس را حفظ می‌کند؛ اگر نسخه از قبل منتشر شده باشد، اسکریپت از جایگزینی خودداری می‌کند. هنگام اجرای مجدد، پیش‌نویس را هم‌زمان Publish نکنید.

## ۴. چک‌لیست پیش از Publish

- [ ] شمارهٔ تگ و برنامه یکی است و CI و گردش Release سبز هستند.
- [ ] هر پنج دارایی وجود دارند و هش فایل‌های دانلودشده با `SHA256SUMS.txt` همان نسخه یکسان است.
- [ ] نصب‌کننده در ویندوز x64 نصب، اجرا و حذف می‌شود؛ پرتابل نیز جداگانه اجرا می‌شود. در نبود WebView2، حالت دریافت/نصب آن بررسی می‌شود.
- [ ] پس از بستن و اجرای دوباره، زبان، تم، تنظیمات و گزارش مورد انتظار باقی می‌مانند؛ داده‌های قبلی قبل از آزمون پشتیبان‌گیری شده‌اند.
- [ ] اعلان پیش از استراحت، دکمهٔ × و تعویق؛ تمرین کوتاه؛ ابزارک؛ تم روشن و تاریک؛ و امتیازهای بدون داده و دارای داده بررسی شده‌اند.
- [ ] قفل سخت‌گیرانه و نگه‌داشتن Ctrl+Shift برای خروج اضطراری، با فعال بودن این گزینه و در محیط امن، بررسی شده‌اند. هم‌زمان کلیک سریع، سینی سیستم و بازگشت رنگ/گاما نیز آزموده شوند.
- [ ] فایل‌ها بدون امضای دیجیتال هستند مگر اینکه جداگانه امضا کرده باشید؛ هشدار SmartScreen و نیاز به WebView2 در یادداشت انتشار توضیح داده شده‌اند.
- [ ] `LICENSE` و اعلان وابستگی‌ها بازبینی شده‌اند. اگر مجوزها یا وابستگی‌ها تغییر کرده‌اند، تعهدات آن‌ها و ارائهٔ سورس لازم را پیش از توزیع بررسی کنید.

برای عیب‌یابی روی همان دستگاه، از PowerShell در پوشهٔ فایل پرتابل:

```powershell
.\ChashmYar-2.3.1-portable.exe --self-test
```

نام را با نسخهٔ مورد آزمایش عوض کنید. نتیجه در پنجره و `%LOCALAPPDATA%\ChashmYar\startup.log` ثبت می‌شود. لاگ ممکن است مسیر کاربر را داشته باشد؛ پیش از اشتراک‌گذاری آن را پاک‌سازی کنید.

## ۵. ساخت و انتشار دستی، در صورت نیاز

روی ویندوز با پیش‌نیازهای [راهنمای توسعه](DEVELOPMENT.md):

```powershell
powershell -ExecutionPolicy Bypass -File .\build-windows.ps1
```

نصب‌کننده و پرتابل در `release/windows/` و مجموعهٔ آمادهٔ آپلود همراه هش و اعلان‌ها در `release/staging/` قرار می‌گیرند. پیش از انتشار، آزمون‌های بخش ۳ و چک‌لیست ویندوز را انجام دهید.

اگر گردش خودکار را عمداً غیرفعال کرده‌اید یا نمی‌توانید از آن استفاده کنید، در GitHub از **Releases → Draft a new release** استفاده کنید، تگ صحیحِ موجود و commit صحیح را انتخاب کنید، پنج فایل `release/staging/` را با drag-and-drop اضافه کنید، توضیحات را وارد و پس از بازبینی Publish کنید. اگر گردش خودکار برای همان تگ فعال است، برای جلوگیری از تداخل ابتدا نتیجهٔ آن را بررسی کنید؛ هم‌زمان دو پیش‌نویس نسازید.

## ۶. خطاهای متداول

- **Mismatch یا تگ نامعتبر:** `npm run version:check` و `node scripts/version.mjs check --tag vX.Y.Z` را اجرا کنید. هر نسخه باید قالب پایدار و با تگ برابر باشد.
- **Assets دیده نمی‌شوند:** ابتدا سبز بودن هر دو job ساخت و پیش‌نویس را در Actions ببینید. Draft عمومی نیست؛ بعد از Publish در مخزن Public نمایش داده می‌شود.
- **خطای 403 هنگام ساخت Release:** مجوز `contents: write` فقط به job پیش‌نویس داده شده است. محدودیت Actions/توکن در تنظیمات مخزن یا سازمان را بررسی کنید؛ توکن شخصی را در سورس قرار ندهید.
- **خطای دانلود NSIS یا WebView2/HTTP 504:** وابستگی خارجی موقتاً در دسترس نیست؛ پس از بررسی شبکه اجرای ناموفق را دوباره آغاز کنید. مسیر WebView2 در زمان نصب نیز به شبکه نیاز دارد.
- **خطای lockfile یا وابستگی:** `npm ci` و `cargo metadata --locked --manifest-path src-tauri/Cargo.toml` را بررسی کنید؛ تغییرات عمدی وابستگی و lockfileها را با هم commit کنید و اعلان مجوزها را به‌روز کنید.
- **SmartScreen یا WebView2:** فایل پیش‌فرض امضا ندارد. Runtime را از Microsoft نصب کنید. بدون بررسی منبع، هش و سیاست امنیتی خودتان هشدار را نادیده نگیرید.
- **ساخت موفق ولی عملکرد اشتباه:** تست مرورگری اجرای قلاب، گاما یا نصب‌کننده نیست. در محیط ویندوز واقعی بازتولید کنید و لاگ پاک‌سازی‌شده را بررسی کنید.

منابع رسمی: [ساخت Release در GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)، [پیش‌نیازهای Tauri](https://v2.tauri.app/start/prerequisites/)، و [مجوزهای GITHUB_TOKEN](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication).
